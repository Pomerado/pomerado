# Changelog

## Unreleased

### Breaking changes

- The local host stages beside authored source exactly the modules `pomerado/runtime` loads, plus `runtime/index.js`, and its own `node_modules/pomerado`, which exports only `./runtime`.
  - `privacy/*`, `runtime/browser-execution.js`, `runtime/capture-diagnostic.js`, `runtime/diagnostic-reasons.js`, `runtime/failure-detail.js` and `runtime/kernel-operation-validation.js` are no longer staged, and an import of the package's internal modules, such as `pomerado/core/runtime/operation`, no longer resolves for authored code. A saved integration that imported one fails to load.
  - Migrate such an integration by importing from `pomerado/runtime` or `../../runtime/index.js`.
- The `mint_update` refusal reason `maintenance` is now `maintenance_setting`, and maintenance adds `output_outside_maintenance` and `owner_unavailable`. Migrate by matching `maintenance_setting` where you matched `maintenance`.
- `ReviewTurn.missingRead` is now `ReviewTurn.followUp`, and `requiredReadRounds` is now `reviewFollowUpRounds`, three rounds: a reviewer sends the host's follow-up in the same review for an outcome the review's kind does not return, once, as well as for a skipped entrypoint read. `ReviewFailure` adds the code `InvalidOutcome` for an outcome still refused after that follow-up, which is not retried as an outage. A private host kind gets no follow-up and fails `InvalidOutcome` at once. `MintHarnessSnapshot` adds the optional `invalidOutcomes`, the attempt's count of such failures, which old and new workers each restore.
  - Migrate a host's own `Reviewer` by calling `turn.followUp` where it called `turn.missingRead`, for up to `reviewFollowUpRounds` rounds, and handle `InvalidOutcome` where it handles `InvalidDecision`.
- A review that returns an invalid outcome twice in a row in one attempt now ends the attempt as incomplete with no host failure, unless the host became unavailable, in which case the attempt ends with the host's failure instead. Diagnostics, including the `mint.execution_failed` event, now report `code: "InvalidOutcome"` for it. Migrate by not treating it as an outage: the first one comes back to the minter as the `mint_update` status `review_invalid_outcome`, now in `taskUpdateStatuses`.
- A maintenance `mint_update` output change may also `add` a field or `tighten` one (optional or nullable to required, or a narrower type), with no confirmation; a `remove` needs `reason`, or it is refused as `output_removal_reason` before review. `PendingTaskUpdate.maintenance.confirmer` may be `none`, for an update that only adds or tightens output fields. A host that compares a repair's output schema against an applied output change must ignore `add` and `tighten`, which loosen nothing.
- Guardian's execution review returns a required `action` label, `read`, `write` or `authentication`, in the shared output format. An execution allow without one fails to decode and is retried like an outage. An allowed `write` on a step without the new `PendingExecution.writeAuthority` becomes a denial.
  - Migrate recorded Guardian responses by adding `action` to every execution allow, and set `writeAuthority` on the steps that may write.
- `MintDependencies.reviewAndExecute`'s dispatch fence is a function of the allow it follows, so every dispatch carries a label: `beforeDispatch(allowed: AllowedExecution)`. Pass the review ID and Guardian's label, or `hostAuthentication` for a sign-in screen the host fills itself.
- The local host's blind-repeat guard and `replayedWriteStep`, `writeStepDigest` and `WriteStep` from `pomerado/core/mint/step-checks` are removed. The harness now refuses a step that repeats an earlier write's entrypoint until the outcome review finds that write did not happen.
- `sessionSentWrite` and `checkWriteSession` from `pomerado/core/mint/write-session` decide whether a write session sent its write from Guardian's labels and the outcome review, not from request counts or commit marks. They take `{ steps }` without `nonReadRequests`; each step carries its `action` label, `possiblySent` and its newest `assessment`. `write_not_submitted` means no step recorded a confirmation and no act step Guardian labelled a write may have reached the site, or the outcome review found each did not happen.
- The minter's prompts are one text for every host. These 33 named authoring sections are now shared text, so a host that composes its own text into the sections drops them. They are `core.example-input`, `core.schema-coverage`, `core.stale-session`, `core.testing-reference`, `core.completion`, `auth.login-url`, `auth.signed-out-flow`, `auth.partial-flow`, `auth.step-fields`, `auth.code-rejection`, `auth.next-screen`, `auth.signed-in-evidence`, `auth.sign-in-check`, `caller-input.declare`, `forms.saved-steps`, `pagination.no-recreated-writes`, `writes.session`, `writes.session-limits`, `writes.finish`, `writes.run-outcomes`, `publication.description-reader`, `publication.login-url`, `publication.confirm-steps`, `publication.input-feedback-end`, `publication.confirm-action`, `agents.workspace-map`, `agents.tools`, `agents.guardian-records`, `agents.guardian-view`, `agents.repeatable-reads`, `agents.write-builds`, `agents.tests` and `agents.capacity`. The other 69 sections stay. The new `core.standalone-completion` section ends the core skill with the local host's summary of its execution and completion, the text `core.completion` held before, so a host that composes its own text adds it. The new `writes.uncertain-status` and `writes.unverifiable-status` sections hold the status a run of a write reports when its outcome is uncertain, `may_have_applied` on the local host.
- `GuardianExecutionEnvironment` gains a required `dataVendor`. It holds the off-site rule's one exception, for the site's own third-party data vendor, and the evidence that shows it on that host. It follows the authorized-site rule in the execution policy. The local host's text says it keeps no network captures, so a request that carries the caller's input to another registrable domain escalates like any other caller data sent off-site.
  - Migrate by passing the exception your host can evidence. The exception 0.3.0 gave every host starts "The site's own third-party data vendor, such as a hosted search service, is the one exception" and relies on screened network captures.
- The package adds a `testing` skill, loaded after `auth`. Its sections `testing.offline-fixtures`, `testing.saved-targets`, `testing.capture-evidence` and `testing.later-cases` have no standalone text. A host that ships its own `testing/SKILL.md` drops it and composes its text into those sections instead.
- `saveSessionCode` from `pomerado/core/runtime/start-state` is now a function of the primary tab's target ID and the site's origin. Its browser call returns a `SavedSession`, `{ state, sessionStorage }`: the context's storage state, and the primary tab's session storage from its frames on the site's registrable domain.
  - Migrate by calling `saveSessionCode(targetId, siteOrigin)`, decoding its result with `SavedSession`, and passing that as the `session` of a `restore` `PageStart`.
- `resetPageCode` takes the primary origin, the site data, the session to restore and the tab storage to restore as separate arguments, then optional extra origins to clear, `cleanupOnly` and `keptCookiePrefixes`. Cookies whose names start with one of `keptCookiePrefixes` survive a clear. `PageStart`'s `restore` takes a `SavedSession`.
  - Migrate by calling `startPage`, which builds the call from a `PageStart`, or by passing the arguments in the new order.
- A sign-in through a security question is saved in `auth-fill.json` as recipe version 1, or version 2 with a popup or approval, with the question's selector on its field. It was version 3. This version still reads version 3 recipes, so nothing has to be built again.
  - 0.3.0 and every later version before this one, 0.4.0-canary.45 to 0.4.0-canary.47 included, refuse such a recipe. A run of an integration built this way fails there with `SignInRunFailed` (`MissingRecipe`, `invalid`) before it signs in or runs anything.
  - Migrate by running such an integration with this version or later, and not rolling back once one is built.
- A run reports a write that returned without recording its declared confirmation as possibly applied, not as a success. A write declared `unverifiable` reports the same. This holds for `run`, `pomerado run` and a served integration MCP.
  - A served write tool whose script declares no write and never calls `verified()` also fails as possibly applied. `pomerado run` is given no effect, so it still returns that script's output as a read.
  - `run` fails with the new `RunOutcomeFailure`. Its `outcome` has the code `outcome_unknown`, the write status `may_have_applied`, `possibleCommit: true` and the retry class `never`. Its `unconfirmed.output` keeps what the script returned.
  - Migrate by catching `RunOutcomeFailure` and reading the site back before any retry.
- Every other run failure that is not a sign-in failure also fails `run` with `RunOutcomeFailure`, including a failure before sign-in, such as the site check, the URL or the start page. Its `outcome` names a finite code, the write status, whether a step may have committed and a retry class. A sign-in failure still fails with `SignInRunFailed`.
  - A write's declared commit steps that were never entered show that nothing was applied only when the site refused the input or the login, or the run couldn't sign in again. Any other failure after a browser step ran may have changed the website.
  - Migrate by reading `outcome.code` in place of the operation's own error.
- A served run's failed job carries `code`, `write_status`, `possible_commit` and `retry`. Its `error` is one sentence for its code, and only a possible commit tells the caller to read the site back before any retry. The sentence that a dispatched action may have taken effect no longer follows every run failure.
  - Migrate by reading `possible_commit` and `retry` in place of parsing `error`.
- `pomerado run` prints an unconfirmed write's output on stdout and its outcome on stderr, and exits 1.
- The minter changes its task with the new `mint_update` tool once the caller confirms the change: input values, a requirement, constraint or prerequisite, the purpose, a read becoming a write, the target site or the login. It replaces the write upgrade and dropping a prerequisite on an answer alone.
  - Removed: `AgentRequest.writeUpgrade`, `MintDependencies.upgradeToWrite`, the `writeUpgrade` option of `MintDependencies.reviewQuestion` and `PendingQuestion.writeUpgrade`, `MintHarnessSnapshot.writeUpgradeDeclined`, `intentWithApproval` from `pomerado/core/mint/review-context` and `writeUpgradeApproval` from `pomerado/core/mint/step-checks`. An older checkpoint's `writeUpgradeDeclined` is dropped as an excess field.
  - Migrate by implementing `MintDependencies.reviewTaskUpdate` and `applyTaskUpdate`. `reviewTaskUpdate` runs `makeGuardian(...).reviewTaskUpdate` against the same pending review the host builds for any other review. `applyTaskUpdate` stores the harness checkpoint it is given (`TaskUpdateApplication.harness`, with the update applied) together with its own bindings, rebinds everything bound to the site for a site change, reruns intake screening and the duplicate check, and resolves the login, all or nothing. It answers `applied` for `next` exactly as given, or `clarification_required` or `refused`. A takeover that restored the checkpoint answers the same `mint_update` again as `updated` without another review, by the update's `requestDigest`. Without both hooks the minter isn't offered `mint_update`.
  - Every review after an update must carry `PendingExecution.taskUpdates`, with `allowedOrigins` rebound to a changed site, and each recorded execution its `taskRevision`. `MintHarnessSnapshot.purposes` entries carry an optional `taskRevision` too. `screenedIntent` is the intent as the owner submitted it.
- `mint_update` takes a `recommend` field, the minter's own judgment: `update` keeps the same task and workflow, and `new_mint` ends the build blocked with its `suggestedRequest`. Besides `updated`, `clarification_required`, `reword`, `new_mint_recommended` and `review_unavailable`, a result may be `update_refused`, when this build can't take the change (a site change while a write session is open or once the build can't run another live example, any change in maintenance, a recommended new build included, or a host refusal), or `update_invalid`, for a request that doesn't decode or a `new_mint` recommendation without a suggested request. Nothing changes on either. A site, login or effect change without an answer in `confirmedBy` is answered `clarification_required` before any review. After a site change, `finish_build` publishes only an execution that ran on the new site (`not_published` with reason `example_before_site_change` otherwise).
- A read build that already ran a live read example can become a write through a confirmed `mint_update`. The write session takes its own example claim, so `claimExample` is called again when its first act step starts, and `finish_build` publishes only what the write session did (`not_published` with reason `example_before_effect_change` for an execution from before the switch).
- An option the minting agent wrote is the owner's words once they pick it or type it back. `ownerNamedOrigins` now takes off-site origins from every answer, picked option labels and notes that repeat an option included, and Guardian's policy says so. `AnsweredQuestion.typed` is removed, and `answersForReview` keeps a note even when it repeats an offered option.
  - Migrate by dropping any use of `typed`. A decoder that ignores excess properties drops it from a stored answer; one that refuses them needs the field removed first.
- Guardian's shared output format adds the outcomes `clarify` and `new_mint`, for the new `update` review kind. `GuardianDiagnostics` correlations add the `update` review kind.
- `JobBuildBlocked` and `MintOutcome.blocked` add the reason `new_mint_recommended`, with an optional `suggestedRequest`.
- New exports: `TaskChange`, `TaskUpdateDecision`, `PendingTaskUpdate`, `ReviewedTaskUpdate` and `taskUpdateForReview` from `pomerado/core/guardian/task-update`; `TaskUpdateRequest`, `taskUpdateStatuses`, `TaskUpdateStatus`, `TaskState`, `AcceptedTaskUpdate`, `TaskUpdateCandidate`, `TaskUpdateApplication` and `TaskUpdateHostResult` from `pomerado/core/mint/contracts`.
- A local build's step asks only the questions its entrypoint declares as a plain literal in its one `defineOperation` call. The host reads them from the source, not from the running script. An ask whose id, prompt or bounds differ fails as `Undeclared` before Guardian's question review, and nobody is asked. A declaration held in a variable, imported or computed declares nothing.
  - Migrate by writing `questions` as an object literal inside the entrypoint's `defineOperation` call.
- A step whose literal `questions` names an invalid id is refused before review, with each id it names.
- A run asks only the questions publication reviewed. A published artifact keeps them as `questions`, an empty object when there are none, and `pomerado.json` saves them. An artifact saved by an earlier release has no `questions`, so it asks only what its entrypoint declares as a plain literal.
- A publication finding carries a required `explanation`: what is wrong, the evidence and the fix, at most 800 characters. Guardian's output format requires it, and a decision whose finding has none fails as `InvalidDecision`. `finish_build` returns each finding's screened explanation and its workspace `file` beside Guardian's `path`, and tells the minter to fix every finding and call again.
  - Migrate by adding `explanation` to every `PublicationFinding` a host makes itself, and to a host's own publication decoder.
- `example_value` is no longer an input finding. An input narrowed to the example's value blocks publication with reason `source_correction`; a decision that returns it as `input_feedback` fails as `InvalidDecision`.
  - Migrate a host's own publication policy by listing only `account_specific_enum` and `input_option` under `input_feedback`.
- A publication finding in Guardian's shared output format carries `quote`, the exact text at fault, in place of `byteStart` and `byteEnd`. The host finds the quote's UTF-8 range in the file Guardian read, first exactly, then with any run of whitespace standing for another. A quote the file does not hold, or a file the host cannot read, puts the finding on the whole file, and the denial stands. The decoded `PublicationFinding` still carries `byteStart` and `byteEnd`, and a reviewer that returns a byte range keeps it.
  - Migrate recorded Guardian publication responses by replacing each finding's byte range with its quote. A host's own publication policy should ask for a quote; core exports its wording as `publicationDecisionPolicy`.
- Guardian's `read_source` tool takes a required `match`, null for a plain read. With a word or phrase, it returns `untrusted_source_matches`: the slices of the whole file around each case-insensitive occurrence, up to 20, each with its byte offset, and the match count. Guardian queries a capture or other large file this way instead of reading it whole. `publicationCaptureQueryPolicy` is the policy's wording for it.
  - Migrate recorded `read_source` calls by adding `"match": null`. A call without it still reads a chunk.
- The authored runtime's `browser/index.js` now imports `browser/outcome-wait.js`. Until hosts compute the SDK's file list from its imports, a host that copies a hand-kept list of the SDK's files into a minting workspace or a run's sandbox must copy it too, or every authored operation fails to load.
  - Migrate by adding `browser/outcome-wait` beside `browser/form-controls` in that list.
- Guardian's publication findings add the category `safety_default`: a safety default that an earlier copy of the source set and the current source drops or weakens. It blocks publication with reason `privacy`, and Guardian's shared output format lists it. A build's `publicationDenial` and a `MintHarnessSnapshot` can carry it, and an earlier version doesn't decode either one that does.
  - Migrate a host's own publication decoder by accepting the category, and a host's own publication policy by including `publicationSafetyDefaultPolicy` (see Other changes).
- Run outcomes add the code `location_not_applied`, retry class `same_key`, so a host's `FailureRenderer` must word it. A script throws the new `errors.LocationNotApplied(message, { field, requested, applied?, step, siteMessage? })` when the page did not apply a location the caller supplied, such as a ZIP code, address or store. The runner code is `LocationNotApplied`. The run fails rather than return results for another place, and the outcome's details carry `field`, `requested`, `applied`, `step`, `site_message` and the script's `reason`. Only a read or a run that left the site untouched gets it: a write that may have changed the site keeps `outcome_unknown`, a confirmed write `execution_failed`, and so does a run that judged a step may have committed. A numeric part, such as a ZIP code typed as a number, is kept as its text. `RunEvidence` gains `location`, and `pomerado/core/runtime/operation-failure` exports `boundedLocationDetail`.
  - Migrate a host's renderer by adding a sentence for `location_not_applied`, and a hosted runner by passing `LocationNotApplied` and its `location` detail through as it passes `InvalidInput` and its refusal.
- `waitForOutcome` (in `outcomeWaitCode` and `waitCode` from `pomerado/runtime`) now fails as `outcome_unknown` once the page shows none of its outcomes and no progress for `noProgressMs`, 8 s by default, where it used to wait out its whole `timeout`. A slow page with no sign the wait recognizes, or whose API is on another registrable domain, can now fail before its `timeout`.
  - Migrate code that relied on waiting out a long `timeout` by passing `noProgressMs` equal to that `timeout`, or by naming the site's loading sign as `loading` and the part of the page the answer appears in as `region`.

### Other changes

- Guardian's publication output policy adds "Unapplied supplied location": code or an output field that lets a run return results when a location the caller supplied did not apply, such as a `store_applied: false` field or a "lookup-only" description, is a `schema_mismatch` finding, while availability the page shows for the applied location stays data with reason `source_correction`. Neither the description nor an answer to a question excuses it. Returning the site's own location when the caller supplied none, and saying so, stays fine.
- The authoring skills settle how a tool treats inputs the page does not take:
  - An option the page lists but greys out, such as a booked date or a sold-out size, is data on a read: the requested value unavailable, with the page's reason and alternatives, and the run succeeds. A write throws `InvalidInput` with `available`. A value the page does not list at all stays `InvalidInput` with `available`. Neither picks another value.
  - `available` for an input that depends on another, such as a check-out after a check-in, is read after the input it depends on applied. Rules the input alone breaks are checked before any site action.
  - A removed or not-found record page is a named outcome that ends in `InvalidInput` with the page's words, never a readiness timeout.
  - A number on a stepped scale, such as a price slider, snaps to the nearest step inside the caller's bound (down for a maximum, up for a minimum), and the tool returns the applied bound. The workspace guide's read-back rule names this and a disabled filter group as the two cases that return results with what applied. The "value the page does not offer" rule covers choice lists only, and a filter group the page disables for a result set is reported, never waited on.
  - Read-back text compares normalized for case and whitespace, locators never use generated CSS class names, and checks that values stopped changing ignore text that changes on its own, such as countdowns.
  - Search results keep related items, recommendations and duplicates out of the matches, and mark a card that stands for a group of variants.
  - The search skill describes a browse tool: when a query names a collection or category, or search results are thin, the minter looks at the site's navigation and offers an optional `category` input beside an optional `query`, at least one required, with the same filters, sort, pagination and cards.
- `report_blocked` takes the reason `host_unavailable` (`BlockedReport`) when the host has ended live execution and what the build still needs cannot run without it, such as the fresh example a source correction needs. It ends the attempt with the host's failure (`hostFailure: "host_unavailable"`), never as blocked, and runs no explanation review; while the host still offers live execution it is refused as `host_available`. `BuildBlocked` and the recorded `blocked` outcome are unchanged. The workspace guidance no longer says a retained receipt may take a source correction once live execution ended: only unchanged source publishes against it. The HTTP skill says to try an HTTP version while building, before the final example, so `finish_build`'s ask is only a backstop.
- One output check for every place that looks at a tool's output: `lintOutput` in `pomerado/core/runtime/output-lint`. It is deterministic and site-independent, and names each finding by field path (array positions folded to `[]`), check and count. It flags script code, style rules, markup and template leftovers, which block publication, and JSON held as text, invisible characters, untrimmed or very long strings, text that may have been read collapsed (a value ending in an expand control's words such as "Read more", the label of an expand control from `controlLabelsFromAriaSnapshot`, a button or on-page link such as "Show more" right after text, or an ending ellipsis on a page that offered one), one field restating its siblings (a whole card's text), repeated entries or records, and list fields that never vary or are always empty, which are flags for the publication review. The blocking checks need strong signals, such as a function or arrow body, a call or assignment on a DOM global, a statement-ending declaration, embedded JSON-LD, a selector block with style declarations, an HTML element's tag or an unreplaced placeholder, so specs, prices, policies and citations that run long with parentheses and semicolons are not flagged. Every pattern's work per character is bounded by a constant, and the leak checks read at most the first 16 KB of a value; a value that is JSON as a whole is never read as script. A field whose schema declares a code or markup `contentMediaType` (`text/javascript`, `text/css`, `text/html` and a few other named code types) keeps its findings, reported as not blocking with that type as their `override`, so the review sees them. The whole-card and repeated-words checks stop at a work budget on very large outputs and mark their findings `partial`.
  - The local host adds `outputChecks` to an execution's observations when its output has findings, with samples, so the minter fixes the read before publishing.
  - `finish_build` refuses a read example whose output still holds a blocking finding, with the new reason `output_checks_blocked` and `MintFailure.outputFindings`, before the contract review. `PublicationRequest.outputOverrides` lets the minter keep any flagged value that is correct as returned, such as code on a tool that returns code or page text that only resembles code, with a reason the publication review checks against the captures.
  - `outputNotes` and `outputNotesPath` in `pomerado/core/mint/output-notes` give hosts the same check at publication: the blocking findings, and `publication/output-notes.json`, every finding with each override and its reason, as host evidence for the publication review. Guardian's publication policy adds `publicationOutputNotesPolicy`, which treats every finding as a lead to verify, never a verdict. Its Lost information rule counts text that ends in or holds an expand control's label, or ends in an ellipsis, as trimmed only when the captures show a fuller copy on the page the tool read, never a snippet the site cuts short itself or an `include` section an example did not ask for.
- `pomerado/runtime` adds `visibleTextCode`, page code that defines `visibleText`, `visibleTexts` and `readRows`. They read only the text a person sees on the rendered page, never a hidden copy, a script, a style or a template, normalize whitespace and remove characters that never show (keeping the zero-width non-joiner and joiner, which spell words and join emoji), read a `display: contents` row through its rendered children, and fail with a `VisibleTextFailure` naming its reason and counts rather than fall back to hidden text. `as: "accessible"` reads what a screen reader reads instead. `readRows` reads a window of rows in one call, and fails as `hidden_only` when rows matched and none is rendered while one still has a box, such as rows fading in from `opacity: 0`; rows with no box at all, such as a no-results page's `hidden` or `display: none` template row, read as `[]`. `normalizeText` applies the same normalization to text outside the page.
- The authoring skills read values with `visibleText` or `readRows`, expand collapsed text before reading it, return each fact once, keep related records out of a list's results, mark a card that stands for a group as a group, and offer costly or bulky parts of a page through one optional `include` input, such as the site's filters, each record's whole text or related records.
- `waitCode` from `pomerado/runtime` declares the page waits `waitForOutcome`, `waitForRows`, `waitForValues` and `waitForChange` and `waitReport()`, over one set of budgets in `timeoutDefaults` (navigation 30 s, action 5 s, `answer` 8 s without progress, `answerCap` 30 s, `settle` 0.5 s, `unchanged` 2 s, `lateFillCap` 15 s). A wait keeps going while the page shows progress (a loading sign, DOM changes in a named `region`, the site's own document or API request in flight, a URL change, or its own reads filling) and fails with a readable reason once it shows none. `outcomeWaitCode` still declares only the names it declared before, `waitForOutcome` and its four `outcomeWait…` helpers, with the rest kept inside, so code that pastes it beside helpers of its own still parses; paste one of the two, never both. A generic loading sign (a busy region, an indeterminate progress bar, a skeleton, shimmer, spinner or loader class) counts only while it is new, and determinate bars and form controls never do, so a page's decoration holds a wait for at most the no-progress window; the site's own sign passed as `loading` counts for as long as it shows. `waitForRows` also waits while a visible sign shows beside its rows, never inside one: one there before the action, in the same number, is the page's own, and any other counts until it and the rows have held for `noProgressMs` with no request the action started in flight, so a sign that never leaves costs one window, never the cap. A request the wait's `action` started counts until it ends, up to `lateFillCap`, and the page then gets `unchangedMs` to render; any other request keeps the page busy for at most 4 s, since long-polls and streams stay open. A request repeated with the same method, URL and body at a steady interval is a poll and is ignored, and requests to one API path with different bodies are not. Without `siteDomain`, the site is the page host's last two labels, or three under a country's shared second level such as `co.uk`. `waitForRows` reads each field from its first visible match and reports a needed field, or a row's key, whose matches are all hidden as `hidden`. `waitForOutcome` adds `noProgressMs`, `loading`, `region` and `siteDomain` and the reason `outcome_unknown`, and its `timeout` defaults to the 30 s cap while the page keeps progressing; its `outcome_timeout` message now also names the progress it saw.
- Guardian's execution policy and the publication finding "Built URL" allow a tool to open a URL built from the site's own pattern, as the authoring skill now describes: a URL the site's controls produced, with only the parts that carry each input filled from the caller's values, through `URLSearchParams` for a query part or `encodeURIComponent` for a path part, every input read back from the page, and the page's controls run once instead when the landing is not an expected answer or a read-back differs. A guessed parameter or route, iterating on URL variants, an opaque filter code the page did not produce in that run, and a built URL without a read-back stay denied. A recorded Guardian response keyed on the exact policy text needs recording again.
- A tool's call that ends with `outcome_unknown`, `values_loading`, `values_timeout` or `change_unknown` now fails as a `BrowserActionTimeout`, as `outcome_timeout` does.
- `probeCallCode` from `pomerado/core/runtime/host-execute` wraps an exploration probe's call so its actions default to the 5 s action budget, and the local host applies it to every call of an `explore` step.
- A read that has not signed in tests itself: the minter plans live test cases from a checklist the host derives from the tool's input and output schemas, runs them in batches and reads every result. A signed-in read keeps its four agent-chosen live tests a step, and a read signed out has none of that limit.
  - The new minter tool `live_tests` has two actions. `plan` returns the checklist, the agent's cases in `test/cases.json` and each case's latest status, result and failure, with the authored source line that threw. `run` runs the named cases, or all of them, as one batch after one Guardian review, each case on a page reset like the example's, and returns every result. A case may also run the next page through the tool's own cursor. The first passing example's receipt carries the plan, so the agent refines its cases once the schemas are settled.

### Fixes

- A request with `maxResponseBytes` but without `buffered-response-v1` in `requires` failed `invalid_request` before sending, with no reason given. `maxResponseBytes` alone now sets the response limit; `buffered-response-v1` alone still selects the 8 MiB default.
- A publication review whose outcome Guardian kept refusing, `InvalidOutcome`, was recorded as a `PublicationDecision` with the recovery `retry`, and later question and task update reviews read that as trusted host evidence while the minter had been told to revise. It now has the recovery `correct_source`, or `ended` when it ended the attempt, and lists `InvalidOutcome` in `failedChecks`. Each review's diagnostics name such a failure `code: "InvalidOutcome"` instead of `ReviewUnavailable`. The first `review_invalid_outcome` answer no longer carries `retryable: true`, which tells the minter to submit the same call again; after live execution has closed, an execution's answer points to the retained receipt instead of a revised execution; and a host that becomes unavailable during the review ends the attempt with its own cause instead of no host failure. A host that matched diagnostics by `code: "ReviewUnavailable"` with `reviewFailure: "InvalidOutcome"` matches `code: "InvalidOutcome"` instead.
- A Guardian question or task update review was asked for the execution outcomes allow, deny or escalate before its own, so it could return `allow` where a question review accepts only `allow_business`, `authentication` or `reword`. The host then retried that review as an outage with backoff, from the same input. Each review's request now lists its own outcomes in `trusted_review.outcomes`, only execution, recovery and publication reviews get the execution outcome policy, and a refused outcome gets one correction in the same review before it fails as `InvalidOutcome`. The harness no longer treats `InvalidOutcome` as an outage: the first in an attempt comes back as `review_invalid_outcome` for the minter to revise or withdraw, and the second ends the attempt incomplete with no host failure, since reviews completing in between kept restarting the outage budget.
- A local build no longer publishes a tool that rests on a sign-in it never verified. A write build could sign in again in the middle of its session, write, and publish with no sign-in, so every later run started signed out. `finish_build` now refuses as `autofill_recipe_not_verified` when a step the publication rests on ran after a sign-in sent the login and before any check verified it, and the build has no verified sign-in to publish. A write rests on every act step of its session, and a read on the example or explore it publishes. A read is refused even when its example ran signed out.
- Guardian's source reads on the local host now find the SDK under `operation/`, where authored source imports it as `../../runtime/index.js` from `src/`. A read of `operation/runtime/index.js` or `operation/browser/form-controls.js` returns the trusted SDK file. It used to fail as unavailable. An authored file at the same path still comes first.
- The local host's SDK files for the minter's workspace and Guardian's source reads now include `runtime/files.js`, which `runtime/index.js` and `runtime/kernel-operation.js` import. A read of it used to fail as unavailable.
- A host can require a site name and summary on a site's first publication, even for a tool that never opens the site, such as one that only transforms its input. Guardian's publication review could read that naming as a claim that the tool uses the site and deny it as an unsupported claim, and the host would not publish without the naming. `publicationDecisionPolicy`, which the core publication policy includes, now says host-required site naming only identifies the site the tool is filed under and is no unsupported claim on its own. A name, description or declared variant that promises site behavior the source lacks is still one. A host with its own publication policy gets this by including `publicationDecisionPolicy`.

## 0.3.0

This release lets the person answering a minting question use their own words on any choice, records each Guardian review attempt's timing, stops runs of a built integration from calling Guardian, and starts runs, live examples and a write session's first step from the site root. It changes answer and question shapes that 0.2.0 cannot read: upgrade every host that reads stored requests or answers before any that writes them.

### Breaking changes

- `ValidAnswer` values change type. A choice's value is `ChoiceValue` (`string | { other } | { option, note }`), and a multiple choice's is `MultiChoiceValue` (`readonly string[] | { options, other?, note? }`). Code that reads `.other` after a `typeof value !== "string"` check, or treats a multiple choice's value as an array, no longer compiles.
  - Migrate with `pickedOption(value)` for a choice's picked option, and an `"options" in value` check for a multiple choice.
- `ChoiceQuestion` gains `allowNote`, and `MultiChoiceQuestion` gains `allowOther` and `allowNote`. Every choice and multiple choice the minting agent asks carries `allowOther: true, allowNote: true`.
- `InvalidAnswer`'s `reason` adds `note_not_allowed`, for a note on a question without `allowNote`.
  - Migrate by giving any exhaustive check or list of reasons the new one.
- `AgentRequest`'s choices are `ProposedChoiceQuestion` and `ProposedMultiChoiceQuestion`, without `allowOther`. A `request_input` call that sets `allowOther` or `allowNote` is answered `question_invalid` and asked again without it.
  - Migrate any recorded model responses that set `allowOther`.
- `isReadOrWriteChoice` now accepts a read-or-write choice with `allowOther`. `AnsweredQuestion` gains optional `other` and `note`.
- Version 0.2.0 cannot read requests or answers in the new shapes: its strict decoders refuse the new question fields, and its `validateAnswer` and `validateKeptAnswers` refuse `{ option, note }` and `{ options, … }` as `malformed`. Upgrade every host that reads stored requests or answers before any that writes them, and do not roll back once they are stored.
- Guardian now reviews the read-or-write question the minter asks first, since it accepts the person's own words. A host whose question review refuses that question must allow it, or the first turn fails.
- New exports: `ChoiceValue`, `MultiChoiceValue`, `pickedOption`, `ProposedChoiceQuestion` and `ProposedMultiChoiceQuestion` from `pomerado/core/runtime/input-request`, and `withOwnWords` from `pomerado/core/mint/contracts`.
- Runs of a built integration, through `run` or a served integration MCP, no longer call Guardian and need no model key. Guardian still reviews minting. A run no longer checks its `intent`, `effect` or `authenticationOrigins`.
  - Migrate by checking a call's intent and effect in your host before it runs, if you relied on the run doing it.
- `pomerado run` no longer requires `--intent`, and it ignores `--intent` and `--effect`.
  - Migrate by dropping both flags. Neither limits what a run does.
- A run, through `run` or a served integration MCP, starts at the site root of its URL and no longer loads the URL's path. `pomerado run` and each served call start fresh, in a new browser context. A library caller's run closes the scope's other tabs and keeps its cookies and storage.
  - Migrate by having an operation that needs a deeper page navigate there itself, as its example already starts at the root.
- A live example, a live test and a write session's first `act` step start at the site root after other tabs close. A build that hasn't signed in clears the cookies and site storage exploration left. A signed-in build restores the session saved right after sign-in, or keeps its session when none was saved. Later `act` steps, explorations and inspections continue the current page. The first live step that isn't reset still loads the request's URL.
  - Migrate by writing example, test and first-step source that runs its flow from the root, as the authoring guide already asks.
- A sign-in check counts only after the build's own sign-in steps typed the login's identifier and a password or code, or the user completed an approval. A code the site sent for that sign-in, which the agent asked for, counts as its code once an explore made a completed `fill`, `type` or `pressSequentially` call with it on a page, frame, locator or keyboard, in a frame on the site or one of its `authenticationOrigins`. A frame with no address of its own, such as `about:srcdoc`, isn't on the site. Keys typed with nothing focused count only when every frame of the page is on the site or one of those origins, since they reach whichever of its documents has the focus. Source that only holds the code, or typing it anywhere else, counts nothing. Before that, the check returns `signedIn: false` with `failed: "credentials_not_submitted"` and leaves the build signed out. Every sign-in step drops the session saved after the last sign-in, a check included, and a check after a confirmed sign-in starts a new one, so checking again is refused.
  - Migrate by sending the sign-in screens' `signInStep` fields before the `signedIn` check, and checking once per sign-in.
- `MintDependencies.priorAttemptMayHaveChanged` is removed, with the notice it added to the agent's first input.

  - Authored source may no longer use these top-level names, compared case-insensitively: `mcp.json`, `.mcp.json`, `.vscode`, `.cursor`, `.codex`, `.gemini` and `.claude`. `deployment.json`, `mcp.mjs`, `readme.md` and `codex-mcp.toml` stay reserved.
  - Migrate by adding the integration with the command in its README, or by copying the entry in `mcp.json` into your client. Read `configPath` as JSON. Integrations minted earlier keep their TOML and still run.
- `MintFailure` adds the reason `definition_login_reference`. A host may refuse publication with it when a tool's definition quotes the build's account reference, and the agent is told which part to rewrite.
  - Migrate by giving any exhaustive check on `reason` a default branch.

### Other changes

- Seven headings that rendered empty in standalone mode now have standalone text, in `core/SKILL.md`, `auth/SKILL.md` and `workspace/AGENTS.md`.
- Section markers are checked strictly in both modes: an unterminated, unspaced, duplicated or foreign section, a stray end marker, a section inside a code fence and any other `pomerado:`, in any case, all fail the load.
- The `pomerado-mcp` bin starts when run through npx or a global install. Earlier versions exited without starting the server.
- The shared core skill suggests typed output: numbers for prices, amounts and counts with the currency or unit in its own field, ISO 8601 for dates and times, minutes for durations and one field per fact. These are suggestions, not checks.
- Guardian's question review allows a question about which sign-in method or account to use, or how to reach the sign-in, when the choices it names match what the page shows. The shared workspace guide says asking it is expected. Guardian also no longer rewords any question only because `allowedEffects` is empty.
- `ScriptQuestionDeclarations` refuses the whole record when any question id is invalid, instead of dropping that entry. A question id starts with a lowercase letter and uses only lowercase letters, digits and underscores, up to 64 characters.
- `MintDependencies.redactCallerText` lets a host remove private values, such as the build's account reference, from what the agent writes for its caller: a request's notice, prompts and option labels, and a blocked explanation. The agent's own transcript is unchanged.
- `MintDependencies.priorAttemptMayHaveChanged` tells the agent of a restarted write build that an earlier attempt may have changed the website, so it reads back before any write. A `not_opened` entry navigation may carry `reason: "prior_effect"` when the host skipped it for that reason.
